## 3. Findings

### 3.1 SERIOUS: Type error, stale adapter (`lib/chapman-transformers.ts:23`)

`LaundryItem` was widened to include `price_wash / price_iron / price_fold / price_hang`, but
`toLaundryItem()` still returns the old 4-field shape. `tests/booking-calculation.test.ts` also asserts
the old shape, so both the function and its test are stale. `toLaundryItem` is not used by any screen, only by the test, so this is a hygiene fix, not a runtime bug.

### 3.2 SERIOUS: Tests cannot run reliably

1. `tests/booking-calculation.test.ts` and `tests/quote-guidance.test.ts` fail to **load** with
 `Expected 'from', got 'typeOf'`. Cause: they import `lib/chapman-data.ts` (for `formatGhs`), which now
 imports `lib/supabase.ts`, which imports `react-native` (Flow syntax). There is no vitest config to handle
 React Native, so pure-function tests are dragged into native code. Fix: move `formatGhs` and other pure
 helpers out of the file that owns the Supabase fetch, or add a vitest alias.
2. `tests/supabase-credentials.test.ts` fails because vitest never loads `.env` (there is no vitest config
 and no dotenv setup), so `EXPO_PUBLIC_SUPABASE_URL` is `undefined`. It is also a *network* test, which
 will always fail in an offline CI. Should become an explicitly opt-in "live" test.

### 3.3 SERIOUS: Hardcoded fallback user ID in customer screens

`'057b4ebf-cbe3-44fc-bd53-781026d50a14'` appears in:

- `app/(tabs)/bookings.tsx:95`, a **guest** subscribes to realtime for that specific account.
- `app/service/[id].tsx:55` and `:86`, a **guest** reads, **inserts, and deletes** `routines` rows under
 that account's `client_id`.

This is a debugging leftover. Whether it currently leaks/corrupts data depends on RLS on `routines`.
which I cannot see (§3.5). It must be removed regardless.

### 3.4 SERIOUS: Laundry item identity mismatch between app and the RPC in git

- The app: `LaundryItem.id` "must be the UUID from `public.laundry_items.id`"; `fetchLaundryItems()` reads
 that table and checkout sends those UUIDs to `submit_mobile_laundry_request`.
- The **latest migration in git** (`20260827_008_…`) validates items against a **hardcoded slug list**
 (`'vest', 'shirt', 'trousers', … 'kente'`), not UUIDs, not `laundry_items`.

If production runs the RPC as committed, every checkout is rejected with
*"Add a valid Laundry item from the catalogue"*. The `console.log("🔍 DEBUG: Items being sent to RPC")`
left in `lib/mobile-requests.ts:48` suggests exactly this was being chased. Either the live RPC was
updated in the dashboard (then git is out of date, see §3.5) or checkout is broken today.
**I need you to tell me which**, see the questions at the end.

### 3.5 MODERATE: Schema drift, three tables exist only in the dashboard

`quote_requests`, `routines`, and `laundry_items` are **not created by any migration** in `laundry-app`
(the only place migrations live). The mobile app depends on all three. Consequences:

- Nobody can recreate the database from git.
- I cannot see whether these tables have RLS enabled or what the policies are.
- The staff app has no screen for `quote_requests`, so **Deep Cleaning / Fumigation / Detailing / Fabric /
 Polytank / Contract requests submitted from the app are invisible to staff** unless someone opens the
 Supabase dashboard.

`docs/1-RUN-ME-database-check.sql` is a read-only script you can paste into the Supabase SQL Editor;
its output answers all of this.

### 3.6 MODERATE: Customer client writes staff-only state directly

`lib/booking-store.tsx` and `app/booking/[id].tsx` `insert`/`update` `quote_requests` straight from the
phone. In particular `setProposedAppointment()` lets the **customer** client write
`appointment_response = 'awaiting-customer'` plus a proposed date, that is a dispatcher action. The
laundry flow got this right (RPCs + RLS + event log); the quote flow bypasses that model entirely. The right
shape is the same as laundry: a `submit_quote_request` RPC, staff-only proposal, customer-only accept/reject.

### 3.7 MODERATE: Manus template leftovers that now actively hurt

The project was generated on the Manus platform and still carries its scaffolding:

| Leftover | Why it matters now |
| --- | --- |
| `package.json` → `dev:metro` sets `EXPO_PACKAGER_PROXY_URL=https://8081-…manus.computer` | If you run `pnpm dev` or `pnpm dev:metro` on your own machine, the Expo Go manifest advertises a **dead Manus host** as the bundle URL. This is a very likely cause of the "recurring Expo Go connection failure" in `todo.md`. `npx expo start` / `pnpm android` / `pnpm ios` do not have this problem. |
| `server/` (Express + tRPC + **MySQL/Drizzle** + Manus OAuth + Forge LLM) | A second database technology in a Supabase project. Only `chapmanGuide.ask` (Chapman AI chat) is used, and it needs a Manus-only API key, so **Chapman AI is broken outside Manus**. |
| `lib/_core/{api,auth,manus-runtime}.ts`, `constants/oauth.ts`, `hooks/use-auth.ts`, `app/oauth/callback.tsx` | Manus OAuth. No screen uses it (auth is Supabase phone OTP). |
| `drizzle/`, `drizzle.config.ts`, `mysql2`, `drizzle-orm`, `drizzle-kit` deps | Unused MySQL schema + deps. |
| `template.json`, `scripts/reset-project.js`, `scripts/generate_qr.mjs`, `expo-qr-code.png`, `todo-hbanl6xi.md` | Scaffolding noise. |
| `app.config.ts` → `scheme: "manuschapmanprestigeclient"`, `logoUrl: "/manus-storage/…"`, `name: "app-template"` in package.json | Off-brand deep-link scheme; dead asset path. |
| `.env` committed to git | Currently holds **only** the Supabase URL and the `sb_publishable_…` key, which are designed to ship inside the app, so this is *not* a leak. Risk is habit: `.gitignore` only excludes `.env*.local`, so the first secret added here would be committed. |

- `app/(tabs)/chat.tsx`, Workers and Chat tabs are mock data (`WORKERS` constant, local messages). Fine for

- `lib/chapman-repository.ts` (`services`/`orders` readers, realtime on `orders`) is prepared but unused, good boundary, keep.

production, so the **live database is the source of truth and the git migrations are
stale**. The second mobile app inside `laundry-app/mobile/` is abandoned. Chapman AI
is dropped for now, so the Manus server could be removed. Device testing is done with

## 7. Still open, requiring the live database

1. **`laundry-app` migration 008 is stale.** Production demonstrably accepts the app's
 UUID items while the committed RPC validates a hardcoded slug list. Either capture the
 live function body into a new migration, or replace it with a version that validates
 against `public.laundry_items` by UUID. Until this is fixed, **`laundry-app` cannot
 rebuild the database.**
2. **`quote_requests`, `routines`, and `laundry_items` have no migration.** They exist only
 in the dashboard. They must be captured before anyone can recreate or migrate the schema.
3. **Non-laundry requests are invisible to staff.** `laundry-app` has a `MobileRequests.tsx`
 page for `mobile_requests` but nothing for `quote_requests`, so cleaning, fumigation.
 detailing, fabric, polytank, and contract requests submitted from the app land nowhere
 staff can see them.
4. **Quote writes come straight from the phone.** `lib/booking-store.tsx` and
 `app/booking/[id].tsx` insert/update `quote_requests` directly, and
 `setProposedAppointment()` lets the customer client write a dispatcher decision. This
 should mirror the laundry model: a submit RPC, staff-only proposal, customer-only
 accept/reject.
5. **RLS status of the three un-migrated tables is unknown.** Run
 `docs/1-RUN-ME-database-check.sql` to confirm.
6. **Bundle ID.** `com.app.chapmanprestigeclient` uses a generic `com.app.` prefix. This
 should be settled before any store submission, because changing it later creates a new
 app identity.
