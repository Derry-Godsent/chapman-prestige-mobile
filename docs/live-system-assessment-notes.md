# Chapman Operations System Assessment Notes

## Accessed pages

The authorised staff system is a Vercel-hosted Chapman Prestige operations dashboard. Its primary navigation currently exposes Dashboard, New Order, Orders, Staff, Clients, Services, Receipt, Payments, Reports, Security, Settings, and System Admin.

The Orders page displayed 210 records, search and date filters, service and payment filters, list and pipeline views, CSV-style export, and an order side panel. The operational workflow supports Received, In Queue, Washing, Drying, Ironing, Packaging, Ready, Out for Delivery, and Completed stages. The visible orders show customer, service, item count, amount, payment state, worker, and date.

The authorised New Order route currently renders the shell and a `Create Order` action but showed no visible order form until that action is opened. No records have been created or modified during this assessment.

After opening the form, New Order supports client search, item or service search, a cart, order date, use-current-price option, express-service surcharge, delivery fee, percentage discount, recorded amount paid, and staff notes. It calculates subtotal, total due, and balance. The form is currently centred on staff-entered laundry-style item orders; it does not visibly capture customer-selected appointment windows, customer-approved quote states, location details, service-specific assessment fields, or measurement evidence.

The Dashboard exposes time ranges for 7 days, 30 days, and 1 year, a refresh action, a notification control, and an operational header. In the observed session, its metric and chart area was not visibly populated, which should be investigated as a data loading or empty-state issue before production use.

The Staff page loaded after a brief delay and currently stores first name, last name, phone, email, password, role, and branch. Its roles include Admin, Staff, Courier, Manager, and Strategist; filters include Active, On Duty, and Offline. The observed staff records show employee name, phone, role, availability status, active/completed counts, and efficiency. This provides a basic assignment foundation, but the observed page does not visibly include worker profile photo, service skill tags, gender preference data, location, capacity, shift or leave calendar, job acceptance, vehicle, or customer-visible bio. These fields are required if the mobile marketplace and live service tracking are to be real rather than illustrative.

The Clients page includes search by name or phone, individual or corporate type filters, loyalty-tier filters, archive status, client creation, edit, archive, delete, and export actions. The visible client list supports name, type, tier, and phone, but several observed records have a zero phone number and duplicate-like names. This means an authenticated mobile account cannot yet be matched safely to a client record using phone number alone. A unique verified mobile-auth identifier, normalized E.164 phone number, duplicate-resolution process, consent fields, preferred communication channel, and address book are required before production synchronization.

The Services page is a strong foundation: it shows 82 items across 18 categories, service filtering, active-status controls, tier discounts, express pricing, export, and configurable per-item rates. It covers Laundry, Cleaning, Fumigation, Car Detailing, Sofa, Subscription, Contract, Fabric, Home, Deep Clean, Carpet, Polytank, and garment categories. Quote-based items visibly use a placeholder rate and custom-quote instruction. The current catalogue should become the single source of truth for mobile service names, prices, add-ons, categories, availability, and effective dates, rather than keeping duplicated app constants.

The Payments page supports payment recording, paid/partial/pending filtering, client or order search, receipt viewing, totals collected, outstanding balance, monthly revenue, and pending-payment counts. In the observed records, methods are predominantly Cash and several pending entries reuse `PAY-000`; there is also one negative balance in historical data. The mobile app’s Mobile Money and Card choices therefore need a real transaction model before they can be represented as completed payments. Add immutable payment transactions, provider reference, method, currency, amount, payment event time, reconciliation state, refund or reversal logic, and receipt delivery. Payment identifiers should never be placeholder or duplicated.

The Reports page provides time-range views, total revenue, net profit, expenses, total orders, average order value, client totals, outstanding balance, daily revenue versus expense charts, busiest days, service revenue mix, and top clients. It is a useful management surface; however, the observed report figures and the payment table appeared inconsistent across pages, while expenses were zero. Establish one reporting source of truth, define the accounting basis, and test report totals against payments and orders before using reports for decisions.

The Security page exposes roles and permissions, access control, audit logs, and session settings. The visible configuration has Worker and Admin roles, and the Worker role currently appears to have access to system administration, security, settings, client records, payments, and staff records. This is materially broader than the least-privilege access required for operational staff. Before mobile integration, define task-based roles such as Dispatcher, Laundry Technician, Field Technician, Courier, Finance, Support, Manager, and System Administrator; restrict each role to the minimum data and actions needed. Customer-facing access must be handled separately from staff roles, and no mobile client should receive a staff-level database key or broad table access.

Settings currently manage the business name, primary phone, address, email, pricing and rules, loyalty tiers, data and backup, and an obscured sheet-protection password. The system indicates that configuration applies to the main branch and other branches inherit settings. Expand this into explicit branch, service-area, transport-zone, blackout-date, opening-hours, appointment-capacity, tax, and notification-policy configuration so the app can offer accurate availability and delivery pricing.

System Administration provides staff-access, permissions-matrix, system-settings, and activity-log sections, as well as role changes and account bans. This is appropriate for a back-office environment, but it reinforces the need to separate it from the customer API. Mobile traffic should use narrowly scoped, server-mediated endpoints with audit logging and rate limits, never the same full administration surface or unrestricted database policies.
